# baseline-refine-hybird

在 `baseline-refine` v4 上增加 B 做市，日志版本为 `baseline_refine_hybird_v1`。
目录名沿用用户指定的 `hybird`。A 做市、B 在线周期学习、历史初始化、冻结止盈目标、
止损确认与持续退出保留原有行为；本目录独立保存策略代码，不依赖原目录中的模块。

这里的 ±100 指 **B 的实际净持仓范围**，不是累计成交量或订单次数。
周期与做市共用同一个 B 仓位、`QuoteManager` 和发送器，不能各自申请 100 股。
A 也独立限制在 ±100；A 的空余额度不能扩大 B 的范围。

## B 如何做市

`B_MM_SETTINGS = MarketMakingSettings(order_volume=20, inventory_band_lots=20)`：

| 状态 | B 的报价行为 |
| --- | --- |
| 没有周期计划 | 每侧最多 20 股，实际仓位加挂单限制在 −20～+20 |
| 周期建仓窗口内 | 保留一次请求全部剩余目标量，最多建到 ±100；反向做市最多回收已观察到的仓位中的 20 股，至少保留 1 股 |
| 周期满仓后 | 多头在 +80～+100 做市；空头在 −100～−80 做市 |
| 建仓 10 秒结束且只成交 37 股 | 多头随后只在 +17～+37 做市，不因做市补到 +100；空头对称 |
| 周期模型失效或信号反向 | 该周期停止增仓，可在原做市区间内减仓；不单独强制平仓 |
| 止盈、确认止损、异常持仓退出 | 停止做市，一次请求关闭全部实际剩余仓位；部分成交后持续处理残量 |
| 退出后的 2 秒冷却、无成交计划后的 1 秒重试等待 | 暂停 B 报价 |

启动后先观察到空仓，才允许把随后产生的无计划仓位纳入做市；启动已有残仓沿用原策略的退出处理。
新周期方向与已有做市仓位一致时，将它纳入统一周期计划；方向相反时先关闭这部分仓位，
完成冷却后再评估新计划。模型尚在学习或没有有效周期规律时，可以继续普通 B 做市；
盘口异常、A/B 不同步、残差冲击和价差过宽时暂停新增风险。过旧或无效 B 盘口直接撤单等待。

做市价格来自扣除自身挂单后的盘口，改善同侧最优价，并保持相对当前外部盘口被动。
一至两 tick 的窄价差中，若周期建仓价会碰到自己的反向做市价，就把做市侧退到更外侧。
API 没有 `post_only` 参数，因此只能保证计算时相对该盘口被动，不能保证行情变化后的 maker 身份。

## 下单方式与成交确认

依据用户提供的 [Optibook API Reference](<../../../Optibook API Reference>)，
`insert_order` 支持 `limit` 和 `ioc`；`amend_order` 只接受新数量，不能改价。

| 场景 | 本版本使用方式 | 原因 |
| --- | --- | --- |
| A/B 做市 | 被动 `limit` | 保留未成交量和合适的旧单，等待成交 |
| B 周期建仓 | 改善同侧最优价 1 tick 的 `limit` | 建仓窗口内保留余单；只有 1 tick 价差时可能立即成交 |
| B 退出前 2 秒 | 改善同侧最优价的 `limit` | 先尝试较好的退出价格 |
| B 退出 2 秒后 | 可成交 `limit`，最多越过最新对手价 10 ticks | 尝试立即成交，并保留未成交残量继续管理 |
| 价格不变且剩余数量合适 | 保留原单 | 不补齐普通做市的每次部分成交，减少不必要更新 |
| 改价、缩量、切换方向、扩充周期建仓量 | `delete_order` 确认后再 `insert_order` | 避免旧单与新单叠加或自成交；不假设改单具备原子的只减量语义 |

**成交确认主动调用 `poll_new_trades`**，按品种和 `trade_id` 去重，按 `order_id` 累计已成交股数。
`FillStream` 是私人成交流的唯一分发入口：执行器下单后可以立即刷新，读到的成交会缓存给
原 `StrategyRecorder`，日志仍能拿到全部回报；没有第二个独立消费者抢走记录器的成交。
`execution_reports` 区分提交量、已确认成交量和尚未确认量，报单 `success` 不等于全量成交。
后续延迟回报继续累计并写入原有 `fill` 日志，空批次不会清除已经确认的成交。

IOC 适合立即撮合并自动放弃残量的尝试，轮询同样能确认它已经发生的成交。
但空批次本身不能说明没有延迟回报。**本版本默认全部使用 limit，不发送 IOC**：
当前需求要求持续处理退出残仓，可成交限价单能立即撮合，也能让未成交部分留在可查询、可撤销的挂单中。
这属于执行方式选择，不表示 `poll_new_trades` 无法确认成交。
成交流用于确认与记录；下单风险核对同时使用交易所实际仓位和全部未成交挂单。

## 额度如何保证

对每个品种分别核对：

```text
实际仓位 + 所有剩余买单 + 新买单量 <= 100
实际仓位 - 所有剩余卖单 - 新卖单量 >= -100
```

反向挂单不能抵消同向挂单风险。混合报价另带 `min_position`、`max_position`，
下单器用更新后的实际仓位重新裁剪每一侧，避免报价生成后发生的成交突破做市区间。
发送器在速率等待结束后再核对硬上限；配置不能把逐品种硬上限调到 100 以上。
改价或扩量先完成两侧必要撤单，再加入新单；撤单失败或无法确认就不重报。

沿用每品种未成交挂单总量 200、所有品种共享每秒最多 200 次更新。
代码保留原 A+B 净值 ±200 的附加检查，但它不能替代各自 ±100 的约束。
这些检查以本进程作为该账户的唯一订单发送者、交易所持仓/订单接口正常工作为前提；
启动前已经存在的越界仓位会进入减仓处理，不会被假装成合法仓位。

## 运行与验证

从项目父目录 `/Users/liuyang/Documents/codes/optibook` 执行：

```sh
rtk proxy python3 -B stock_market_making/strategies/baseline-refine-hybird/run.py --check
rtk proxy python3 -B -m unittest discover -s stock_market_making/strategies/baseline-refine-hybird/tests -p 'test_*.py' -q
```

部署时同步整个策略目录以及已有的 `stock_market_making/recording`、`quote_helpers.py`。
Notebook 的参数、报价和主循环定义共用 `strategy` 标签；`--check` 会编译这些单元，
并校验周期、做市和执行器参数，不需要连接交易所。

在安装了 Optibook SDK 的交易环境中手动启动：

```sh
python stock_market_making/strategies/baseline-refine-hybird/run.py --live
```

日志写入 `data/runs/baseline-refine-hybird`，行情仍写入共享 `data/market`。
每条报价包含 `market_making` 区间、`cycle_position` 和每侧 `execution_policy`。
停止程序取消挂单但保留残仓，沿用 baseline-refine 的语义。

测试覆盖原周期回归、混合状态切换、双边额度、部分成交、撤单失败与成交竞争、
1000 轮有固定随机种子的成交序列、私人成交流分发，以及模拟交易所中的实际 Notebook 主循环。
2026-09-11 验证：79 项测试、`--check` 和完整 Notebook 定义加载均通过。
仅进行离线验证，没有连接交易所或验证混合策略的实盘收益。两种逻辑共用 B 的实际仓位，
日志不把 B 收益拆分成独立的周期收益和做市收益。
